## 二、deviceToken 完整生成算法（1.5.4，已离线验证 MATCH）

```
deviceToken = base64( "WEB#" + deviceId + "#" + cipherB64 + "#" + len + "#" + md5 )

deviceId = APP_KEY + "-h-" + <页面加载 ms 时间戳> + "-" + <32 hex uuid>
cipherB64 = base64( AES-128-CBC( 设备指纹串, key=动态key, iv="0123456789ABCDEF" ) )
动态key   = AES-128-CBC-decrypt( DeviceConfig 字段[0] 的 base64, key="FqJB6iRNVYdEGpwb", iv="0123456789ABCDEF" )
            → 16 字符 ASCII，如 "1d23483593c11f7e"
len       = 服务端/内部另一个长度值（本次 1190/1336 不等，与明文长度无线性关系；不影响 InitCaptcha 被接受）
md5       = MD5( "WEB#" + deviceId + "#" + cipherB64 + "#" + len + "#daye,raolewoba!" )
```

**验证记录**（`verify_token_md5.js`）：
```
md5 段 227b84c4d98947e2cc6e6af6dc7de66f
MD5("WEB#deviceId#cipher#1190#daye,raolewoba!") = 227b84c4d98947e2cc6e6af6dc7de66f  ✅ MATCH
```
**关键新增常量：盐 `daye,raolewoba!`**（旧版本 1.5.1 无此盐，len 语义也不同，不要再拿旧样本推）。

## 三、data 字段结构（轨迹，1.5.4，已还原明文）

生成链（页面 hook `btoa` 抓到三段中间物）：
```
TrackList 对象 → JSON.stringify → (tk() 处理) → pako.deflate → 自定义编码 → 前 3 字节写魔数 25 13 27 → btoa
```
- `data = base64( 0x25 0x13 0x27 + enc )`，`enc` 长度 ≈ deflate 长度 × 4/3 − 3
  （实测：deflate 449 → enc 597；deflate 639 → enc 849）
- 自定义编码使用**动态符号表**且带混淆（`enc` 的字节分布覆盖 0..252，非 ASCII，205 种不同值），
  实现位于**动态 JS**（`https://g.alicdn.com/captcha-frontend/dynamicJS/3.29.0/pe.0xx.<hash>.js`）
  的 JSVMP 解释器内（`pe:286608` / `pe:211175` 调用 btoa），不在 `feilin075.js`，也不走 `__ALIYUN_CRYPT`（crypto-js）。

明文 JSON（deflate 解压后，示例 1444 字节）：
```json
{"TrackList":{
  "mc":"627,749,22236, ,0",                 // mousedown 点
  "tc":"",                                  // touch
  "mu":"1147,749,22806, ,0",                // mouseup 点
  "te":"",
  "mp":"639,750,2384,0|651,749,2397,0|...",  // mousemove 路径 x,y,t,flag
  "tmv":"",
  "mm":"627,749,22235,0|...|1319,861,22823,1", // 全部 mousemove，最后的 flag=1 = 异常点

**关键**：`mm` 里 `flag=1` 的点就是非可信事件（合成事件 / 越界坐标）标记 —— 这是失败的直接嫌疑。

### AST 插桩结果（2026-11-12 02:45）

```
instrumentation(install, "**/dynamicJS/**", mode="ast",
  rewrite_member_access=true, rewrite_calls=true,
  filter_property_names=["fromCharCode","charCodeAt"], on_oversized="selective")
```

- 改写成功：`files_rewritten=1`，`total_edits≈10`（首次不带 calls）；带 calls 后 tap 总量 **10956 条**
- 统计：`string.charCodeAt` **7714 次**、`function.fromCharCode` **3234 次**
- 逐点配对（`charCodeAt` 的返回 → 紧随的 `fromCharCode` 输出）得到 **107 组 `in === out` 的恒等映射**，
  值域含 `1020 / 1012 / 65525 / 65527`（>0xFF，是 UTF-16 码位中转），**不是加密映射**

**判定**：`enc` 不是逐字符变换出来的，而是**数值数组一次性转字符串**——
与 `pe.0xx.js` 里 `a += String.fromCharCode.apply(null, n)` 的写法完全吻合（n 是 subarray 分块）。
即：加密在 VM 里把字节写进数组，最后 `fromCharCode.apply` 拼成 latin1 串再 `btoa`。
所以 tap `fromCharCode/charCodeAt` 只能拿到"结果"，拿不到"填充过程"。

**唯一可行的下一步**：`hook Array.prototype.push`（或 `Uint8Array.prototype.set`），
在 data 生成窗口内按「数组长度增长到 597/849」筛出目标数组，记录其全部元素写入 —
才能解出 `enc = F(deflate, key, nonce)` 的逐字节公式。预估成本：一轮完整采样 + 一次日志裁剪。

### 阶段 0：oracle 判定（2026-11-12 03:10，已执行）

`oracle_probe.js`：5 组，每组独立 `InitCaptcha` 取新 `certifyId` 后提交一次 `slideAuth`。

| 组 | data 处理 | 响应 |
|---|---|---|
| 0a 控制 | 页面真 data（632 字符） | `{"captchaVerifyResult":false,"bizResult":false}` |
| 0b 破坏 | 第 10 字节 XOR 0xFF | 同上 |
| 0c 魔数清零 | `25 13 27` → `00 00 00` | 同上 |
| 0d 截断 | 去掉尾部 32 字节 | 同上 |
| 0a2 重复 | 真 data 再来一次 | 同上 |

**响应体去重后只有 1 种 → oracle 不可用**：服务端不区分「data 解不开」与「解开了但校验不过」。
按 skill 纪律，纯协议无法靠响应差异做小步逼近，验收只能走「**离线等价**」——
即 Node 生成的 data 必须与页面生成的 data 在相同 `deflate + nonce` 下**逐字节相等**，这要求解出 `F`。

   在 `btoa` 前 50ms 内过滤，定位 597 字节缓冲的逐段写入；
3. 拿到「同一位置、不同内容」的两条 tap 记录，即可解出 keystream 公式（与 key/nonce 的关系）；
4. 若 keystream 依赖服务端 nonce，则 data 无法离线生成 → 只能走「页面出 data（R5）」，
   而页面出 data 必须真实指针输入（`isTrusted=true`），否则服务端判失败。

## 四、slideAuth 失败归因（重要）

做过的对照实验：

| 实验 | gap | 轨迹 | 结果 |
|---|---|---|---|
| 页面自提交（5 次，各种 gap） | 未校准 | 合成事件 | `captchaVerifyResult:false` |
| 页面自提交，亮块法 gap 205（**图片目视确认缺口就在 205**） | ✅ 正确 | 合成、人类化变速 | `false` |
| Node InitCaptcha（浏览器 token） → 浏览器产 data → Node slideAuth | gap 232（图片确认正确） | 合成、人类化 | `false` |

- **位置已经不是瓶颈**：s2 样本 gap=205 与图片目视完全一致，`slidePos≈205`，仍被拒。
- **会话/密钥不是瓶颈**：Node InitCaptcha 用浏览器 deviceToken 直接被接受，说明 deviceToken + Log1 密钥可跨进程复用。
- **结论**：拦截点在 **轨迹可信度** —— SDK 会把 `isTrusted=false` 的合成事件写入 `TrackList.mm`（flag=1），
  服务端行为模型据此判失败。**合成 DOM 事件（`new MouseEvent`）永远 `isTrusted=false`**。

**实测确认（2026-11-12 02:00）**：主世界 `evaluate_js` 里 `new PointerEvent('pointerdown', …).isTrusted` 返回
`false`（浏览器硬性属性，无法伪造）。因此只要走"合成事件"路线，data 里必然带不可信标记。
按当前约束（不使用 Playwright 原生输入），**slideAuth 无法通过**，这条路的终点就是 S2。

### data 长度规律的第 3 个样本（补充验证）

同一会话再采样一次（deflate **367** 字节）：

```
data = magic(3) + 489 字节      // 489 = len(base64(367)) - 1 = 490 - 1
```
与前述 `449→597`、`639→849` 一致：`enc_len = len(base64(deflate)) - 3`（±1 取决于 padding）。
这条规律是把编码层判定为「等长替换」的关键证据，也是后续复现时必须满足的硬约束。

# 七、RDP 断点调试能力（Firefox 152，非 CDP）——已打通并实测

camoufox 是 Firefox，Playwright 侧走 Juggler、没有 CDP，因此「断点 / 单步 / 调用栈 /
作用域 / 暂停中求值」在 Playwright API 里拿不到。这里改用 Firefox 原生 RDP
（`camoufox.exe -start-debugger-server <port>`），把等价能力补齐，且全程不经过 Playwright。

## 7.1 协议结论（逐条实测，可直接照抄）

| 步骤 | 请求 | 说明 |
|---|---|---|
| 列标签页 | `{to:"root", type:"listTabs"}` | 返回 tabDescriptor |
| 取 target | `{to:<tab>, type:"getTarget"}` | `frame` 里**同时**带 `threadActor` 与 `consoleActor` |
| 激活线程 | `{to:<thread>, type:"attach", options:{}}` | **`options` 必填**；缺了不会进入 RUNNING，`sources` 恒为 0 |
| 校验 | `{to:<thread>, type:"isAttached"}` | `{value:true}` |
| 列脚本 | `{to:<thread>, type:"sources"}` | `{sources:[{actor,url,isInlineSource,...}]}` |
| 可断行 | `{to:<sourceActor>, type:"getBreakableLines"}` | `{lines:[...]}` |
| 取源码 | `{to:<sourceActor>, type:"source"}` | 大文件返回 `longString`，需对 `longString` actor 发 `substring` 分片 |
| 下断点 | `{to:<thread>, type:"setBreakpoint", location:{sourceId,line,column}, options:{condition,logValue,showStacktrace}}` | key 是 `sourceId`/`sourceUrl`，不是 `actor` |

## 7.2 三个踩过的坑

1. **残留进程劫持端口**：`proc.terminate()` 只杀启动器，真正的 camoufox 仍占着
   `-start-debugger-server` 端口；下一次 launch 会静默连到**旧浏览器**（症状：`sources`
   里是上一页 URL、`conn0→conn1→conn2` 不断增长、断点永不命中）。
   现在 `launch()` 先按命令行筛选并杀掉带 `-start-debugger-server` 的进程（不动
   Playwright 拉起的浏览器）。
2. **`attach` 缺 `options`**：thread 停在 DETACHED，`sources` 永远 0，且不报错。
3. **导航后 actor 全换新**：`reload` 之后 `child2 → child3`，旧 thread 上的断点失效，
   必须重新 `enable` + 重下断点；`debugger_reload` 已自动完成。

## 7.6 XHR/网络断点（抓请求入参的最佳手段）—— 已实测

`thread.setXHRBreakpoint {path, method}` 是真实可用的（不是空实现）：
服务端通过 `http-on-opening-request` 观察者实现，`paused.why.type == "XHR"`。

**关键坑**：`method` 必须传 `"ANY"` 或真实方法名。服务端判断是
`method !== "ANY" && method !== requestMethod` 才跳过，传空串永不命中
（这是本地 XHR、真实站点 fetch 都试过的结果）。

实测（真实站点，`captcha.refresh()` 触发）：

```
setXHRBreakpoint {path:"", method:"ANY"} -> {value:true}
paused  -> why={"type":"XHR"}            <- fetch 也命中
frames  -> 58 层（压缩后的 webpack/VM 栈，displayName 如 r3/r3</</<、lG/lG</e</J.K）
scopes  -> 每层 bindings 可读；函数作用域里能看到 VM 的局部名
```

注意：`frame_evaluate` 里写 `(function(){...arguments...})()` 拿到的是**这个 IIFE 自己的**
arguments，不是被暂停帧的；要读帧实参得用 `(function(a){...})(arguments)` 形式，
或直接引用帧作用域里的具名变量。

用途：`data` 生成在 VMP 内部，行断点无从下手；网络断点能停在「请求即将发出」那一刻，
再配合 `frames` 逐层向上走，就能定位构造 URL/body 的那一帧。

## 8.2 `data` 生成链（**已证明**，两组同轮真实样本逐字节 0 差异）

```
payload = nonce_hex(32 字符) ‖ JSON{TrackList,TrackStartTime,VerifyTime,xPos,slidePos,arg}
T       = base64( zlib.deflate(payload, level 6) )        // T 恒以 "eJ" 开头
data    = base64( armour(T) )                             // 与 T 等长，前 3 字节天然是 25 13 27
```

`armour`（无密钥，只依赖构建常量）：
```
SEED = "3e627e1b4c63f913"
r    = 64 项固定表（见 feilin_data.js 的 ARMOUR_TABLE）
阶段1: for i=0,t=0..63 { t=(((i+t)+r[i]+r[t])>>1) + SEED.charCodeAt(i%16)) & 63; if(i!==t) swap3xor(r,i,t); }
阶段2: for i, e=0, a=0 {
          a=((e^a)+(r[e]^r[a]))&63; if(e!==a) swap3xor(r,e,a);
          m = T.charCodeAt(i)+e+r[e]; m -= (a+r[a]); m ^= (r[e]+r[a]); m ^= r[(r[e]+r[a])&63];
          out += fromCharCode(m & 255); e=(e+1)&63;
       }
```
落点：`pe.0xx` 的 VM 小程序 `F`（解释器 `L`、调用点 `tc:296633`；btoa 由 `F` 内部 `u.C="btoa"` 发起）。

**纠正**：
1. 前文「`len(enc) ≈ len(deflate) × 4/3`」是误读——armour 输出与 `T` 等长，那 3 字节本来就是输出的前缀。
2. 前文「魔数 `25 13 27` 是常量」错——它是**产物**：SEED 固定 + T 恒以 `eJ` 起步，前 3 字节自动算出。这解释了静态搜 `251327` 永远搜不到。
3. 前文「flag=1 标记不可信」**写反了**：`mm/mp` 第 4 段与 `mc/mu` 第 5 段的 flag，**1 = 可信输入（isTrusted）**，0 = 合成。用 `user32.SendInput` 注入真鼠标事件时 174/479 点全 1，用 `dispatchEvent` 时全 0。

## 8.11 滑块轨迹的定量基线（首次沉淀，2026-11-13）

> skill 的 `cases/` 里没有滑块/轨迹类案例（8 个案例均为 JSVMP/签名/环境补全），本节即为该方向的第一条。

### 真人轨迹的实测特征（`config/human_cvp.json`，540 点）

| 指标 | 值 | 含义 |
|---|---|---|
| `mm` 点数 / 跨度 | 540 / 4515ms | 约 8.4ms 一点 |
| `mm` dt | 中位 6ms，p25 5ms，p90 11ms，max 276ms | 硬件采样 ≈166Hz，含 1~2 次 200ms+ 停顿 |
| 每步 `dx` | **中位 1px，p90 2px**，最大 137px（末点 tail） | 手指是"极细地推"，不是大步跨 |
| 速度 | 中位 0.167 px/ms，p90 0.400 | — |
| 单调性 | 前段/后段 dx **无负值**，全程单调不减 | **没有回拉** |
| `mp` | 906 点 / 12872ms | 含按下前在页面上活动的过程 |
| flag | 全 1 | 可信 |

### 反例：我用"闭环补偿"造出来的轨迹（已证伪）

```
我们后 12 步 dx: 107 107 -35 -35 -102 42 42 -58 -60 79 0 133
```

`finger += (target - piece) * 0.55` 这类"按块的实际位置回压手指"的补偿，会在块缓动滞后的情况下形成**正反馈震荡**：手指冲过头 → 块追上 → 手指回退 → 块回退……

**判据（可复用）**：
1. `dx` 序列里**不应出现大幅负值**（真人 0 个负值；出现 ±30px 级交替即为脚本特征）；
2. 相邻 `dx` 不应反复变号（真人加速度符号翻转虽多，但幅度都在 ±2px 内）；
3. 落点靠**轨迹设计**（贝塞尔终点=目标），不靠"边拖边修"；
4. 如果一定要修，只允许**单向微调**（差多少前移多少），且最多 1~2 次。

### 结论
轨迹形态可以做到与真人统计不可区分（点数/dt/速度/单调性全部对齐），但该站点的 `slideAuth`
仍然返回 false（12 次，含页面原生 POST 与全新 profile）。
所以**"轨迹不像人"不是本站点的拒绝原因**；同样的对齐在极验/易盾等站点是可以过的
（见 slider-captcha-lab 的 16/16、17/17）。

剩余未排除项只有两条：
1. 服务端不可观测的信号（硬件级时间戳 / 设备侧一次性序列）；
2. **频率/IP 降权**——我们同一出口连打 12 次，而真人成功发生在第 1 次。

要区分，需换 IP + 冷却 30~60 分钟 + 只打 1 次。

```
帧数 90~130，总时长 0.8~1.3s

### 关键教训

1. **"点数越多越像人"是错的**：543 点/4.4s 全 false，92 帧/0.88s 通过。
2. **"平滑"是最大的机器指纹**：人手的本质特征是**变速**（谷底犹豫 + 末端甩鞭），不是匀滑。
3. **末端回拉是真特征**：55% 概率拖过头再拉回，我原来一条轨迹里没有负 dx。
4. **`data` 长度不是指标**：成功的两次 dataLen 只有 1304/1528，之前那些 4688/16300 全 false。

### 另一项目补充（black-mouse-sha/aliyun-slider-solve）

- **拼图位移是二次关系**：`piece.left = 0.0769·m + 0.003552·m²`，反解 `D = (-A+√(A²+4B·target))/(2B)`。
  本站在 C 的受控标定下是线性（`slidePos = 手指位移/2.5`，600→240），**换站点需重新标定，不要照抄系数**。
- **`navigator.webdriver` 必须为 false**，且要 `addInitScript` 早于页面脚本；否则轨迹再像也判 `F001`。
  纯协议不涉及浏览器，但 **deviceToken 里的环境指纹可能带此标记**，换设备来源时需注意。

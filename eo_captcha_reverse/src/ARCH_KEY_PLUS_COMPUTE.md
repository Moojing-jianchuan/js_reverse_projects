## 它和我们做法的差别

| | 我们的做法（R3 跑 VM） | 它的做法 |
|---|---|---|
| 出 collect | 在 Node `vm` 里**跑整份 tdc.js**，让 VM 自己采集+加密 | **静态从 tdc.js 挖出 4 个 32 位 key**，用纯 JS 实现加密 |
| 环境数据 | 手写/回放 env，缺一项就少一块 | **Hook 真实浏览器一次，把指纹数组直接搬过来** |
| 动态部分 | 把 build 绑定的密钥也一起交给 VM | 只处理"每次 build 变的东西"（key），其余纯算 |
| 结果 | `collect≈4200`，`errorCode=12` | `collect_len=7552`，`errorCode=0` |

关键点：**`tdc.js` 每次现场生成、密钥 build 绑定** ⇒ 不必还原算法本体，只要每次从当前 `tdc.js` 里
**提取 key（4×32 位 + 若干字节码偏移）**，再对"明文 = 一组固定的指纹数组"做纯算加密即可。

## 由此产生的两步计划

1. **解出一次明文**（解锁一切的前提）：用从 `samples/cur_tdc.js` 提取的 key，解密配套的
   `samples/dumped_cur.json` 里的浏览器 collect。解出来后就知道：
   - 明文的确切结构（字段名、顺序、哪些是数组、有没有二次压缩）
   - 我们本地 `collect` 少的 216 块（1728 B）到底是什么字段
   → 已派子任务 `713f851e` 执行（产出 `src/TDC_KEY_FINDINGS.md` + `tools/tdc_key.mjs`）。
2. **Hook 一次指纹数组**：解出结构后，按字段清单在浏览器里一次性采齐（`readPixels/getImageData/字体/媒体/
   webgl 参数/layout/事件统计`），之后完全离线纯算出 collect。

## 注意（结论强度）

- 截图是**别人的实现**，只能当"方向可行"的观察证据，不能当我们自己的验证。
- `collect_len=7552` 比我们浏览器实采的 `4888~5084` 长，说明它的明文比"单次页面采集"更完整
  （可能是多轮采集合并/更多字段），解出明文后要对齐的正是这个差异。

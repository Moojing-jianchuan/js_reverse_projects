## 1. 本轮拿到的关键事实（全部实测）

### 1.1 页面侧（真实浏览器，人工过码后）

| 步骤 | 观察 |
|---|---|
| `mapping` | 200，11 个品类 |
| `info` 首次 | **485 请校验验证码** |
| `captcha/call` | 200，10895 字节挑战（**图集拖拽题**：6 张 118×118 小图 + `#captchaSubmit`） |
| 人工过码后 `captcha/verify` | 200，23 字节 `{"code":1,"msg":"验证成功"}` |
| `info` 重试 | **200，14740 字节**（加密响应） |
| 页面渲染 | **商品卡片数 = 0**（`a[href*="/product/"]` 为 0，body 文本仅 997 字符） |

**结论①：即使 info 返回 200，页面也没有渲染商品** —— 说明响应解密/业务链路在本环境未闭环。

### 1.2 服务端对请求体的要求（同一放行会话内做三组对照）

| 请求体 | 请求头 | 结果 | 解读 |
|---|---|---|---|
| 明文 `{sign,...}` | 只有常规头（UA/Origin/Cookie） | **485 请校验验证码** | 缺风控头 → 触发验证码 |
| 明文 `{sign,...}` | **复制放行态的整套风控头**（adi/hsn/ltk/sessionid/shumeiid/sk/sks/traceparent） | **400 `校验失败:11001`** | 头通过了，**body 格式不合规** |
| `{data}` 信封（原样重放 id 87） | 同上一行 | **403 请求已拒绝** | 信封**一次性/防重放** |

**结论②：服务端强制要求 `{data}` 信封**，明文体在当前版本被判为格式错误（与 2025-11 的 CSDN 文章不同，版本已升级）。

### 1.3 本地能否自己造信封？—— 目前不能

`{data}` 的结构已确认与 captcha 的 `d` **同形但不同表**：

| 项 | captcha 的 `d` | info 的 `data` |
|---|---|---|
| 前缀 | — | `md5(明文)`（已验证：`df74e652...` = md5 明文） |
| 密文/明文长度 | 1301 / 1301（等长） | **125 / 124（+1 字节）** |
| keystream | `F(sk, 浏览器族)`，已标定 | **与 captcha 完全不同**（偏移 0~4 扫描，匹配率 0~0.8% ≈ 随机） |

**结论③：`{data}` 用独立的 keystream，且多 1 字节（疑似版本号/盐）。** captcha 的标定结果不能直接复用。

### 1.4 pceptor 是信封与解密的所在

- pceptor 加载后会 `POST https://dav.dewu.com/interceptor`（596B，内容是一组灰度开关：`isAnti:0`、`gray558h5CookieDomainsk:yes`、`gray559webSkCookie:yes` 等），配置已存档 `artifacts/interceptor_resp.json`
- 拦截器 `_yundunxhr` 同时覆盖 `XMLHttpRequest` 与 `fetch`，伪造成 native 外观
- `fun.Fun110(明文, bcv, sk, sm)` 不是信封构造器，而是**令牌组生成器**（返回 `{a,b,e}` 48 字符令牌 + `c:"2,hdw4"` + `d` 明文直通）
- 响应体的解密入口疑似 `fun.Fun99(respText, '', sks, '')`（未确认）

## 4. 判断与建议

- **纯协议采集 info 目前不成立**：卡在 pceptor 的两项密码学（信封加密 / 响应解密），不卡在算法理解 —— 因为这两项都可以用「喂入-截出」在 jsdom 里逼出来，工程量中等但路径清晰。
- **验证码是逐次人工的**：本轮拿到的是图集拖拽题（需人眼），不是无感 type=2。批量采集还会不断撞验证码。
- 因此现实可行的产出顺序应是：先把 pceptor 的信封 + 解密吃下来（一次性成本），再讨论频率与验证码策略；否则只能在浏览器里一页一页人工过码。

# 得物「图集验证码」识别器 — 设计、实测与失败模式

> 目标：给一张「目标小图」+ 5~6 张候选图，输出「哪张候选包含目标物体」的下标。
> 纯 Node / 纯 CPU / 完全离线（不联网、不用浏览器 MCP）。
> 代码：`src/captcha_recognizer.js` ｜ 测试：`scripts/test_recognizer.js` ｜ 结果：`artifacts/recognizer_test_results.json`

## 0. TL;DR

| 结论 | 数据 |
|---|---|
| `image` 字段**不是物体照片**，是 **100×21 的「文字标签」**（样本为「沙发」，透明底黑字） | 灰度 webp 380B；`aspect=4.76`、`brightRatio=0.84`、`inkRatio=0.03` |
| 候选是 5 张 **80×80 照片** + 1 张 `blank.png` **URL 占位**（下标不固定：样本 A 在第 5，样本 B 在第 0） | 页面 CSS 的 118×118 / 76×16 只是**渲染尺寸**，资产本身是 80×80 / 100×21 |
| **纯 CV 无法完成「文字标签 → 照片」匹配**（不在同一特征空间）；这是本任务的硬边界，不是调参能解决的 | 见 §6.1 |
| 已实现三条通道：`crop`（物体裁剪题，**合成基准 36/36 = 100%**）、`label`（标签+类目记忆库，**1-shot 留一 2/2 但 margin 仅 0.01~0.04**）、`oracle`（`bgImage` 块投票，**2/2 且与人眼一致**） | 见 §5 |
| **意外收获**：响应里的 `bgImage` 就是**正确答案候选的大面积马赛克降质版** → 生产环境可零视觉模型直接定答案 | A 样本 50/64 块归属候选 0，B 样本 26/64 块归属候选 3 |
| 单题耗时：crop 中位 **~80ms**（P90 ~115ms），oracle/label 仅 **40~50ms** | 80×80 候选 × 6 |

```
scripts/make_contact_sheet.js   生成带标注的联系图（目标图 / bgImage / 6 张候选 + 黄金标签绿框）
data/label_gallery.json         标签指纹 → 历史答案图（类目记忆库）
artifacts/captcha_dump/*.png    已落地的人眼可看图（target/bg0..5/bgImage/sheet）
```

```bash
npm i sharp                                  # 唯一新增依赖（webp 解码 + 重采样，prebuilt，无需编译）
node scripts/build_label_gallery.js           # 自举类目记忆库
node scripts/test_recognizer.js               # 全量自测（--quick 少量样本）
node scripts/recognizer_cli.js artifacts/capture_call2.json
node scripts/recognizer_cli.js artifacts/capture_call.json --no-oracle   # 纯视觉模式
```

`recognize(input, options)` 签名：

```js
const { index, scores, confidence, meta } = await recognize(
  { image /* dataURL */, bgList /* dataURL[] */, bgImage /* 可选 dataURL */ },
  { mode: 'auto'|'crop'|'label'|'oracle', gallery /* 记忆库 */, labelText /* 仅标注用 */ }
);
// index      : 命中的候选下标（0-based，与 bgList 顺序一致）；占位项永不当选
// scores     : 与 bgList 等长的相似度数组（占位项为 0）
// confidence : 0~1，按通道做了天花板校准（见 §7）
// meta       : channel / targetType / labelFp / ranked / detail(逐项中间量) / warnings / elapsedMs
```

## 2. 验证码的真实形态（实测，不是推测）

### 2.1 字段对照（`captcha/call` 响应 `data`）

| 字段 | 实测内容 | 说明 |
|---|---|---|
| `image` | `data:image/webp` 100×21，380B | **文字标签**（透明底黑字），样本内容「沙发」 |
| `imageUrl` | `29BC94BB….png` | 与 `bgImageUrl` **共用同一个资产 ID 前缀**（该 ID 在样本 B 里换成 `22395EC1…`，但 `image` 字节完全相同 → 同一类目下多个商品条目） |
| `bgList` | 长度 6：5 个 `data:image/webp` 80×80 + 1 个 `https://davstatic.dewu.com/captcha/blank.png` | **占位项是 URL，不是 dataURL**；下标随机（A=5，B=0） |
| `bgImage` | `data:image/webp` 80×80 | 见 §3.2：**正确答案图的马赛克降质版** |
| `no` / `sessionId` | `20133046278` / `SbvO1iVT…` | 题号 / 会话 |

> ⚠️ 任务书里提到的 `artifacts/cap_call_resp.json`、`artifacts/cap_challenge.json` **在仓库里不存在**。
> 实际可用的真实样本只有 2 个：`artifacts/capture_call.json`、`artifacts/capture_call2.json`
> （另外 `capture_verify.json` 是 verify 请求，不含图）。**这是本轮所有统计 n=2 的根因。**

### 2.2 尺寸链：页面尺寸 ≠ 资产尺寸

| | 页面渲染 | 资产实际 |
|---|---|---|
| 候选 | 118×118 | **80×80** |
| 相框占位 | 118×118 | `blank.png`（URL） |
| 目标小图 | 76×16 | **100×21** |

两者比例都是 1.475 与 1.31，说明浏览器只是等比放大。**识别器必须工作在资产原始分辨率**上，
否则等于在插值出来的像素上做匹配（凭空造高频）。本实现一律按 `fit:fill` 拉伸到自身工作尺寸
（缩略图 32×32、HOG 64×64、模板匹配上限 160 长边），与页面 `object-fit:fill` 的形变保持一致。

### 2.3 两个「图看起来全黑」的解码坑（都踩过，已修）

1. **单通道灰度 webp**：`info.channels = 1`，若按 4 字节步长读 RGBA，会读到别的通道 → 亮度全 0。
2. **透明底**：题目图是 `rgba(0,0,0,0)` 的黑字 + 全透明背景。不 `flatten` 到白底，平均亮度恒为 0，
   `brightRatio` 全 0，于是「白底文字」判别失败、文字标签被误判成照片裁剪。
   → 修法：`sharp(buf).flatten({background:'#fff'})` 后再读；按 `info.channels` 步进规范化。

修复前 vs 修复后的判别输出（同一张 100×21 题目图）：

```
修复前: lum.mean=0.00048 std=0.0013  → type=crop   inkRatio=1.00 brightRatio=0.00   ← 错
修复后: lum.mean=0.94749 std=0.1906  → type=label  inkRatio=0.03 brightRatio=0.84   ← 对
```

## 3. 「标准答案」怎么来的 —— 三方交叉定标

官方响应里没有答案字段，离线无法直接知道真值。本轮用**三条互相独立的证据**定标，三者完全一致：

| 方式 | 样本 A（`capture_call.json`） | 样本 B（`capture_call2.json`） |
|---|---|---|
| ① 人眼看图（已落盘 `artifacts/captcha_dump/`） | 候选 0 = 红沙发客厅 | 候选 3 = 绿沙发客厅 |
| ② **oracle**：`bgImage` 逐块归属投票 | **#0**，50/64 块，票占 81.6% | **#3**，26/64 块，票占 41.0% |
| ③ 语义：标签「沙发」 | 该图确有沙发 | 该图确有沙发 |
| **结论** | **0** | **3** |

### 3.2 `bgImage` 到底是什么（本轮最重要的意外发现）

`bgImage` 不是「底图背景」，而是**正确答案候选被大面积马赛克覆盖后的降质版**：

- 块内标准差图显示大量**完全平坦**的块（马赛克格），未打码区仍保留细节；
- 取 8×8 网格块均值，逐块找「最接近的候选」，归属高度集中：

```
样本 A（红沙发）块归属，计数 [50, 3, 2, 6, 3, 0]        样本 B（绿沙发）块归属，计数 [0, 6, 12, 26, 15, 5]
00000000                                                33333333
00000000                                                33333343
00000000                                                34344444
00002200                                                34344444
00000003                                                33553411
34010033                                                32222212
04400113                                                31222155
00300000                                                32222315
```

- 与候选 0 / 3 的 8×8 块均值加权相关分别 0.85 / 0.41，其余候选全部 <0.2 甚至负相关。

**工程含义**：生产环境里 `bgImage` 一到位，答案可以直接反查，**不需要任何视觉模型**。
这也是为什么 `recognize` 支持 `bgImage` 可选入参并默认优先走 `oracle` 通道。
（n=2，机制解释成立且两块图都吻合，但样本太少 —— 见 §8。）

### 3.3 人眼复核图

`node scripts/make_contact_sheet.js` 会生成带标注的联系图（第一行：目标图 / bgImage / #0 / #1，
第二行：#2~#5；**绿框 = 黄金标签**，灰框 = URL 占位）：

- `artifacts/captcha_dump/capture_call/sheet.png`  → 目标图「沙发」，bgImage 是 **#0 红沙发客厅**的马赛克版，★标在 #0

## 4. 算法选择与理由

### 4.1 为什么不用 CLIP / 为什么"不硬上"多模态

- **本机没有任何可用的 onnx/模型文件**（`python` 只有 `onnxruntime`+`numpy`，无 torch、无模型权重；
  `tesseract` 未安装；`~/.cache` 下无任何 `.onnx`）。硬拉一个 CLIP 需要一次性下载 100MB+ 权重，
  且中文标签还需要中文 CLIP / OCR 配套，链路长、离线性被破坏、n=2 也没法验证。
- 更关键：**样本里的题目图是文字**。CLIP 的文本塔可以直接吃「沙发」二字，但它需要真实的图文对齐
  权重才能区分 5 张 80×80 的插画风照片；在没有验证集的情况下，这属于"看起来高级但无法证伪"的方案。

### 4.2 三条通道 + 各自的度量

| 通道 | 适用 | 度量（本实现） |
|---|---|---|
| **`crop`**（物体裁剪题） | 题目图是候选的局部/同款 | **多尺度零均值 NCC**（10 个尺度 0.35~2.1，积分图算窗口均值/方差）+ 颜色直方图相交 + HOG 相关 |
| **`label`**（文字标签题） | 题目图是文字 | **标签指纹** → **类目记忆库**：与历史答案图比 **HOG 主导** 的图-图相似度 |
| **`oracle`**（有 `bgImage`） | 任意 | **8×8 块均值归属投票**（按"次小距-最小距"加权），票占 = 得分 |

`crop` 融合式：

```
score = 0.60 · clamp(NCC_max) + 0.20 · histIntersection + 0.20 · HOG_corr
```

`label-gallery` 权重（`W_GALLERY`，**颜色权重归零**）：

```
score = 0.90 · ((corr_HOG + 1)/2) + 0.10 · ((corr_thumb32 + 1)/2)
```

为什么这么调，是有数据支撑的。同一批候选、跨样本 1-shot 检索（A 的答案图 → B 的候选）：

| 描述子 | A图→B | B图→A |
|---|---|---|
| 空间颜色直方图 | #2 ✗ (0.32) | #2 ✗ (0.51) |
| **HOG-lite 4×4×8** | **#3 ✓ (0.23)** | **#0 ✓ (0.23)** |
| HSV 直方图 | #5 ✗ | #2 ✗ |
| 亮度布局 8×8 | #2 ✗ | #4 ✗ |
| layout + hog 拼接 | #2 ✗ | #4 ✗ |
| 空间色 + hog 拼接 | #2 ✗ | #3 ✗ |

> 复现：`node scripts/probe_descriptor_compare.js`。真正的沙发对（红沙发↔绿沙发）**颜色直方图相似度是全场最低**
> （`hist=0.246`，因为一红一绿），只有梯度方向结构能把它们排第一。所以记忆库检索里颜色必须清零，
> 这也解释了为什么"多加特征"反而更差（拼接后 HOG 被稀释）。

`meta.detail` 里保留了每项的中间量（`ncc`/`at`/`scale`/`hist`/`phash`/`hog`/`votes`/`blockShare`），
方便人工复核到底是哪一路把某张顶上来的。

| `label`（带记忆库） | **3** | ✓ | 1.000 | 0.615 | 0.385 | 0.550 | 40ms | 0, 0.615, 0.589, **1.000**, 0.472, 0.526 |
| `oracle`（bgImage） | **3** | ✓ | 0.410 | 0.226 | 0.185 | 0.615 | 44ms | 0, 0.098, 0.190, **0.410**, 0.225, 0.076 |

> `label` 行的 top1=1.000 是**自匹配**（记忆库里就有这张图本身），**不能当准确率**，它只证明"管线通"。
> 真正的准确率看 §5.3 的留一检验。
> `auto`（纯视觉）两题全错，且置信度被刻意压到 0.15 —— 这正是设计意图：**不确定就说不确定**。

### 5.2 oracle 通道：2/2

```
capture_call.json   → index=0  HIT conf=0.890  票型 {0:50/82%  1:3/5%  2:2/1%  3:6/10%  4:3/2%}
capture_call2.json  → index=3  HIT conf=0.615  票型 {1:6/10%  2:12/19%  3:26/41%  4:15/23%  5:5/8%}
```

样本 B 的票更分散（答案 41%，第二名 23%）→ 置信度自动从 0.89 掉到 0.62，符合"马赛克更重"的直觉。

### 5.3 `label` 通道：跨样本 1-shot 留一（唯一诚实的准确率）

用 A 的答案图当记忆去 B 里找同类，再反向（**绝不与自身比对**）：

| 训练 → 测试 | index | 命中 | conf | scores |
|---|---|---|---|---|
| A → B | 3 | ✓ | 0.238 | 0, 0.572, 0.598, **0.607**, 0.573, 0.488 |
| B → A | 0 | ✓ | 0.276 | **0.607**, 0.472, 0.473, 0.567, 0.549, 0 |

**2/2 命中，但 margin 只有 0.010 / 0.039，第二名咬得很紧**（B 题的 #2 帆船 0.598 对 #3 沙发 0.607）。
结论：机制方向对（HOG 能把"室内家具场景"和"海面/草原/星空"分开），但**证据强度不足以支撑自动提交**，
所以 `label-gallery` 的置信度被硬性压在 ≤0.55。

### 5.4 `crop` 通道：合成裁剪基准 36/36 = 100%

做法：从候选图里随机裁 40%~85% 的块当「目标小图」（真值 = 该候选下标），随机缩放到 76~116px 宽、
webp q70~90 重编码；每源再补一个「极端压缩」用例（缩到 30px 宽 + q25）。
题源包含**正确答案**和**两个干扰项**（后者检验"是否真的按内容排序"，而不是碰巧偏爱某张）。

```
合成基准 top1: 36/36 = 100.0%   随机基线 20%
  答案源 10/10   · 答案源/极端压缩 2/2
  干扰源 20/20   · 干扰源/极端压缩 4/4
top1 均值 0.720 · top2 均值 0.531 · margin 均值 0.189（最小 0.037，最小 top1 0.506）
单题耗时：中位 ~80ms · P90 ~115ms · max ~118ms（多次运行 78~81ms 波动）
```

> 注意基准的性质：这是「**同源内容**检索」——题目图确实来自某张候选的像素，属于 crop 通道的
> 目标工作场景，而不是"同类不同图"的泛化测试。它证明管线正确、对缩放/重压缩稳健，
> 但**不能**外推成"真实 crop 题 100%"。真实 crop 题还会遇到同款不同角度、遮挡、水印（见 §6.4）。

### 5.5 其它

- **确定性**：同输入两次 → index 与 scores 完全一致（无随机数参与评分）。
- **耗时**：oracle/label 40~50ms；crop 中位 ~80ms（10 尺度 × 80×80 滑窗，积分图优化）。
- **占位项**：`blank.png` 是 URL → 标记 `placeholder:true / reason:'not-dataurl'`，得分恒 0，
  永不当选，同时**保留下标对齐**（这是最容易写错的地方：样本 B 的占位在 0，若过滤掉会让后续下标整体前移）。

## 6. 已知失败模式

### 6.1 【硬边界】文字标签 vs 照片：纯 CV 无解
样本里的题目图是**文字**。`image` 与候选照片不在任何可比的像素/颜色/梯度空间里，
相似度排序本质是噪声（实测 `auto` 纯视觉两题全错，scores 差异 <0.13）。
这不是调参问题：
- 要读懂「沙发」→ 需要 **OCR**（本地无 tesseract/无中文识别模型）；
- 读懂之后把"沙发"对到 5 张照片 → 需要**语义模型**（CLIP 类）或**类目分类器**（ImageNet 类）。
当前实现只能靠 `label-gallery`（前提：该类目在记忆库里已有答案图）+ `oracle`（前提：响应带 `bgImage`）。

### 6.2 尺寸/形变
- 资产 100×21 vs 页面 76×16、资产 80×80 vs 页面 118×118：若在页面尺寸上做匹配等于在插值像素上匹配。
- 目标图与候选的长宽比通常**不一致**，本实现统一 `fit:fill`（与页面一致）——好处是不过度裁掉内容，
  代价是各向异性拉伸会让 NCC 在极端比例（如 5:1 的标签）上失效；这类图本来就该走 `label` 通道。

### 6.3 平坦/纯色候选
`nccMax` 对 `tnorm < 1e-6`（纯色模板）与 `varw <= 1e-9`（纯色窗口）直接跳过，
`isBlankLike` 把 `lum.std < 0.02` 视为占位。风险：如果真实答案是一张**大面积纯白底商品图**，
会被误判成占位而永不当选。样本里（插画风照片）没有这种情况。

### 6.4 同款不同图（crop 通道的真实天花板）
NCC 只对"像素真正重叠"敏感。真实业务里目标图可能是**同款不同角度/不同配色/带遮挡/带水印**，
这时 NCC 会掉到 0.2 以下，融合分会退化成"颜色+纹理"的粗排。本轮**无法验证**这一点（没有这类样本）。

### 6.5 `label-gallery` 冷启动 + 薄 margin
- 记忆库为空（新类目、清缓存）→ 通道直接退化为 0.15 置信度的弱先验；
- 实测 margin 0.010~0.039，第二名随时可能翻盘；记忆库需要**每个类目 ≥3 张**才有工程意义；
- 记忆库目前由 `bgImage` oracle 自举（`build_label_gallery.js`）—— 若哪天 `bgImage` 语义变了，记忆库会静默污染。

### 6.6 统计效力：n=2
所有"准确率"（oracle 2/2、label 留一 2/2）在 n=2 下**没有置信区间可言**（二项分布 95% CI 下界约 16%）。
合成基准 36/36 是"同源检索"，样本量够但没有泛化意义。

### 6.7 `oracle` 的边界
- 依赖 `bgImage` 存在且是"答案降质版"。若某次响应 `bgImage` 缺失、或降质方式改变（例如全图马赛克），
  票型会摊平 → 置信度自动降到 0.6 以下（样本 B 41% 票 → 0.615），但**不会报错**，只会"安静地低置信"。
- 阈值提示：`top1(票占) < 0.25` 时本实现会再打 0.7 折，视为打法不确定。

## 7. 置信度阈值建议

`confidence = clamp01(0.60·top1 + 0.40·clamp01(margin/0.20))`，再按通道设天花板：
`oracle ≤0.98`、`crop ≤0.92`、`label-gallery ≤0.55`、`label-weak ≤0.15`。
`label-gallery` 还要按证据数打折：`×min(1, 0.5 + 0.12·support)`（support=1 → 0.62，=2 → 0.74）。

| 置信度 | 建议动作 | 对应实测场景 |
|---|---|---|
| **≥ 0.75** | 直接提交 | `oracle` 样本 A（0.89）、`crop` 合成基准里的强匹配（0.84~0.91） |
| **0.55 ~ 0.75** | 可提交但记录样本；建议再跑一次新题对比 | `oracle` 样本 B（0.615）、`crop` 弱匹配（0.53~0.65） |
| **0.35 ~ 0.55** | 不提交，换题（重新 `captcha/call`） | `label-gallery` 自匹配（0.55）、`crop` margin<0.09 的用例 |
| **< 0.35** | 视为不可用（当前实现主动压到这里） | `label-weak`（0.12~0.15）、`label` 留一（0.24/0.28 —— **这次猜对了但要当错的处理**） |

一句话：**把 0.35 当"能不能用"的分界线，0.75 当"敢不敢自动提交"的分界线**。
另外务必同时看 `meta.margin`：`margin < 0.05` 时即便 top1 很高也不要提交（crop 里出现过 0.506/0.427 这种贴身战）。

## 8. 还需要什么信息才能确证准确率

1. **更多真实样本**（最关键）：至少 **30 个** 不同的 `captcha/call` 响应，覆盖不同标签词与不同候选组合。
   单个响应 ~15KB，30 个也就 0.5MB。
2. **端到端回执**：每次 `captcha/verify` 的响应（成功/失败、`feedback` 码）。有了它，
   准确率不用"结构推理"，直接是**提交成功/失败**的真值；也能反过来验证 `bgImage=答案` 这个结论在不同日期是否稳定。
   样本 A 的 `feedback` 字典里已有 `1004 操作正确校验失败`，说明失败原因可分——很值得统计。
3. **标签词表**：如果 `image` 是有限词池（看 `imageUrl` 资产 ID 复用情况，很可能只有几十个词），
   那么**人工标一次「标签指纹 → 词」**就能启用真正的语义通道（甚至不需要 OCR：指纹去重即可）。
   当前 2 个样本的标签指纹都是 `L7e73e23c66964156`（都是「沙发」）。
4. **一条语义通道**（若要彻底摆脱 `bgImage`/记忆库）：
   - 轻量：ImageNet 系分类器（MobileNetV2 ~14MB ONNX）+ 中文词→英文类目映射表；
   - 通用：中文 CLIP（文本塔直接吃「沙发」）。
   接入点已经留好：`recognize(..., {mode:'label'})` 里 `label-weak` 分支就是给"外部语义打分器"留的插槽。
5. **一组真实 crop 题**（题目图是物体裁剪而非文字）用来验证 §5.4 的 100% 是否能外推。

## 9. 附：本轮踩过并修掉的坑（供后续复用）

| # | 坑 | 症状 | 修法 |
|---|---|---|---|
| 1 | `bgList` 里有 URL 项 | 直接 base64 解码抛错 / 下标错位 | URL → `placeholder`，保留下标、得分 0 |
| 2 | 灰度单通道 webp | 亮度恒 0、判别全错 | 按 `info.channels` 步进规范化 |
| 3 | **透明底文字图** | `lum.mean≈0`，文字标签被当成照片 | `flatten({background:'#fff'})` |
| 4 | 颜色直方图当主力 | 红沙发 vs 绿沙发 → 答案排**倒数第一** | gallery 权重里颜色清零，HOG 主导 |
| 5 | 特征越拼越全 | 拼接后 HOG 被稀释，2/2 → 0/2 | 单通道单主特征，权重实测标定 |
| 6 | "自匹配"当准确率 | 记忆库含答案本身 → top1 恒 1.000 | 必须做跨样本留一（§5.3） |
| 7 | 弱先验输出高置信 | 纯视觉乱猜也能给 0.5+ | 通道级天花板（label-weak ≤0.15） |
